Decisions I made that the primary must reconcile: (1) Runtime attribute names had no prior art; I pinned config, kernel, actors (Mapping keyed by unit_id), facade, event_bus, app, mcp_server_factory(principal=...) returning FastMCP, clock, generation_coordinator, audit_event_factory, and repository handles intents/observations/authorizations/audit/schedule. (2) CONFIG GAP: StorageConfig (database_path, busy_timeout_ms) is mandatory in ControllerConfig, so ADR-0003 D1's "in-memory when no database path is configured" branch is inexpressible; simulate=True is the only in-memory composition path. (3) No IntentRepository implementation ships anywhere (memory.py has only observation/authorization; sqlite.py only audit/schedule) — build_runtime must supply the in-memory intent store itself. (4) observe_only permits policy=None; what the kernel evaluates against in that mode is unspecified — my minimal config builds observe_only without policy and does not pin the substitute. (5) Authentication ambiguity: AuthenticationConfig is optional in observe_only yet create_api_app requires an Authenticator; I pin that an unauthenticated request is ALWAYS 401 authentication_required (deny-all when authentication is unconfigured). Positive authentication in tests (secret://operator_credential_ref resolution) is unresolved and needs a primary decision; I deliberately avoided write_enabled builds to dodge eager-secret-resolution failures. (6) Eager validation pinned as ValueError (ValidationError subclasses it) using model_construct-corrupted configs (duplicate unit_id, empty fleet, whitespace unit_id) — composition must revalidate, not trust pre-constructed instances. (7) Boot pins coordinator epoch == 0 at construction (boot is not an invalidating event) and actors BOOT at construction, OBSERVE_ONLY only after explicit start(); actor fence() is proven to advance the one shared fleet coordinator, but kernel/facade sharing of that coordinator is not externally observable and rests on construction faith. (8) The construction ban is sockets+tasks only; SQLite file creation at build is expected and asserted. (9) I did not pin the D5 inhibit-acknowledge route (facade/REST agents own it); route assertions are superset-based so its addition stays compatible. ## Findings

### [1] P1 - Awaiting repository handles while isinstance-pinning the shipped synchronous SQLite classes forces inheritance shims
Category: test-gaming / contract-conflict

Lines 436-437 require runtime.audit/runtime.schedule to be instances of SQLiteAuditRepository/SQLiteScheduleRepository, whose methods are synchronous (sqlite.py:161 `def append(self, event) -> None`, :202 recent, :261 get). The same suite then awaits those handles: line 444 `await runtime.schedule.get()`, line 453 `await prior.audit.append(...)`, line 471 `await restarted.audit.recent(limit=10)` — awaiting a sync None/Plan return raises TypeError. The classes cannot be made async because the committed baseline pins their sync call style (tests/unit/test_repositories.py:219-324 calls append/publish/current directly and consumes return values). Meanwhile ControlKernel (control_kernel.py:133-210) and EnergyPodActor (actor.py:298-363) already await their repository ports, so build_runtime must produce async adapters regardless — but a has-a wrapper (the natural composition shape) fails the isinstance pins; only async subclasses of the shipped sync SQLite classes can satisfy both suites. The behavioral SQLite proof (database file created, cross-build audit reuse at lines 435/471-474) already covers durability, so the type pins add shape-forcing without adding contract coverage.

Suggested fix: Drop the isinstance pins on runtime.audit/runtime.schedule (keep the simulate-mode negative type checks plus the existing behavioral proofs: db file exists, audit reuse across builds, schedule.get() works), or have the primary explicitly ratify async-subclass adapters of the SQLite repositories as the contracted composition shape and record it in API_CONTRACTS.md.

### [2] P1 - Boot-disarmed and no-authority-restoration proven only in observe_only; write_enabled restart and any authenticated path never exercised
Category: safety-coverage

Line 137 fixes mode=observe_only for every build in the file. API_CONTRACTS says the process starts disarmed "regardless of prior state" and CONTINUITY makes boot-disarmed a non-negotiable invariant, but the only restart test (lines 447-482) composes observe_only, where restored authority could not reach hardware anyway. A write_enabled build_runtime that reconstructed an ARMED actor or re-granted authorizations from the durable ACTIVE-lifecycle audit history (exactly the seed _prior_active_audit_event plants) passes this suite. Additionally, the only ASGI request ever driven is unauthenticated (lines 364-367), so the deny-all 401 is the sole app-level pin: the composed app could be wired to a stub service (create_api_app with a different facade) and still pass, because the 401 fires in middleware before any service call. Both gaps share the unresolved secret://operator_credential_ref resolution seam the author flagged.

Suggested fix: Add a write_enabled boot test (valid PolicyConfig + enabled AuthenticationConfig, with a decided credential-resolution seam or injected authenticator) asserting actors construct in BOOT and stores are empty despite ACTIVE-lifecycle durable history; add one positively-authenticated request proving the served app returns the composed facade's data (site_id from config).

### [3] P1 - One-fleet-coordinator and event-bus wiring rest on construction faith; kernel/facade edges never observed
Category: coverage-hole

Only the actor-to-coordinator edge is proven (lines 542-548). A composition that builds a second AuthorityGenerationCoordinator and hands it to the facade and kernel passes every test: facade.emergency_stop "immediately advances the fleet generation" (API_CONTRACTS) is never asserted against runtime.generation_coordinator, and nothing verifies facade.snapshot's snapshot_sequence comes from runtime.event_bus (line 328 only checks it is an int). Likewise ADR-0003 D3 "Audit appends and observation publications are events" is unpinned at composition level: appending to runtime.audit or runtime.observations never has to advance event_bus.snapshot_sequence(), so a bus constructed but wired to nothing satisfies the suite. D1's core claim — ONE fleet-wide coordinator and a connected graph — is exactly the part the suite cannot see.

Suggested fix: In a simulate build with started actors, call runtime.facade.emergency_stop(principal=OPERATOR, ...) and assert (await runtime.generation_coordinator.snapshot()).epoch advances and the latched stop appears in runtime.intents; assert initial facade snapshot_sequence equals runtime.event_bus.snapshot_sequence(); assert appending an audit event or observation advances the composed bus's snapshot_sequence.

### [4] P1 - D6 fail-closed supervision path pinned nowhere: no lifespan, no task start, no fence-on-failure
Category: safety-coverage

The suite pins only the negative: construction starts no tasks (lines 387-396). Nothing in this file or test_main_entry.py ever proves the other direction — that serving the composed app (ASGI lifespan or another explicit start) launches the kernel tick loop, per-unit actor loops, and event publication, nor that "supervisor or task failure fences every generation and runs actor shutdown with the bounded-zero contract" (API_CONTRACTS runtime section; CONTINUITY invariant). test_main_entry.py:580-599 injects a server_runner that raises before supervision exists and only asserts a nonzero exit code. A composition whose app lifespan starts nothing — serving read-only snapshots while the kernel never ticks and actors never poll — passes both suites green.

Suggested fix: Drive the composed app's ASGI lifespan (scope type "lifespan") or an explicit start handle: assert supervision tasks exist, then fail one (e.g., a kernel tick error) and assert the fleet coordinator epoch advanced, authorizations were revoked, and actors ran shutdown with the bounded-zero attempt before the process reports failure.

### [5] P2 - D1's in-memory-when-no-database-path branch is inexpressible and the suite silently encodes the narrowing
Category: contract-conflict

ADR-0003 D1 grants "repositories (SQLite when a database path is configured, in-memory otherwise)", but StorageConfig.database_path is required and its validator rejects ":memory:" and empty strings (runtime/config.py:240-247), so the no-path branch cannot be expressed. The suite hard-codes the narrowed reading — simulate=True (line 151) as the only in-memory composition path — without any test or marker flagging that a documented contract branch is unreachable. CONTINUITY requires doc/code/test conflicts to be classified and resolved in the authoritative documents before tests are accepted; this conflict is silently resolved in favor of the narrower behavior.

Suggested fix: Have the primary amend ADR-0003 D1 ("in-memory otherwise" -> "in-memory in simulate mode / when no durable store is configured") or make StorageConfig optional in the configuration contract; then reference that resolution in the test module docstring so the suite no longer encodes an unratified narrowing.

### [6] P2 - Task-set snapshot diff cannot detect tasks that start and finish during construction
Category: weak-assertion

Lines 391-396 diff asyncio.all_tasks() before/after compose with two sleep(0) yields. Any task build_runtime starts that completes or dies inside the construction window — an eagerly-started actor connect failing instantly under the socket ban, or a fire-and-forget kernel tick that runs once and returns — is absent from the diff and undetected. The tests that assert BOOT lifecycle (lines 310, 482) run without the socket ban, so eager start-then-crash behavior is never combined with the ban. The socket ban itself is sound (module-attribute patching catches socket.socket/create_connection/socketpair at call time, including asyncio.open_connection's internal socket creation).

Suggested fix: Inside the ban test, also assert every actor's lifecycle is UnitLifecycle.BOOT immediately after compose, and/or monkeypatch asyncio.create_task (and Task) during the compose call so any start attempt, however short-lived, fails loudly.

### [7] P2 - Revalidation of model_construct-corrupted configs is pinned without contract grant
Category: contract-conflict

Lines 399-428 require build_runtime to raise ValueError on configs corrupted via ControllerConfig.model_construct (duplicate unit_id, empty fleet, whitespace unit_id). The contract grants only "Construction validates wiring eagerly; a misconfiguration raises before any task starts" — an already-validated ControllerConfig is the contracted input type, and pydantic documents model_construct as an at-your-own-risk validation bypass. An implementation that trusts the typed config (validated by the configuration suite at parse time) and validates only wiring fails these three tests. The fail-closed direction is defensible defense-in-depth, but as written the tests invent a revalidation requirement and force a model_dump/model_validate round-trip on every build.

Suggested fix: Either have the primary ratify "build_runtime revalidates the configuration" in API_CONTRACTS.md's composition section, or reframe the corrupted-config cases as wiring errors the contract already implies (duplicate/unknown unit ids surfacing during actor construction) rather than pinning full pydantic revalidation.
