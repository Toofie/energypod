## Findings

### [1] P1 - Emergency stop has no degraded-dependency tests: fence-first invariant proven only on the happy path
Category: safety-coverage

The only tests that set any fake to failing are the two health tests (lines 662-665, 677). The safety-critical ordering pins (fence < bounded-zero < audit, epoch advance before return) are asserted only when every port succeeds. Concrete failure scenario that stays green: an implementation whose emergency_stop calls intents.add() first and propagates the OSError when the intent store is down, never calling coordinator.advance() or any actor request_bounded_zero() -- outstanding kernel-minted authorizations remain live and unpublishable-as-revoked, and the suite cannot detect it. The same hole covers audit.append failing during stop (CONTINUITY: revocation must fence before any potentially blocking audit operation), actor zero failure, coordinator.advance failure, bus.publish ordering relative to the fence (bus publication is never position-checked even though the fake records it), and emergency_stop with unknown unit ids (must it still latch/fence the known units? fail-closed direction unpinned).

Suggested fix: Add a deformed emergency-stop matrix: intents.add raises, audit.append raises, actor request_bounded_zero raises, coordinator.advance raises, and a stop naming an unknown unit -- each asserting the generation still advanced and bounded-zero was still requested before any audit work or error propagation. Pin bus.publish position relative to the fence.

### [2] P1 - Contracted facade behaviors with zero coverage: disarm, acknowledge_inhibit, and schedule/kernel composition
Category: contract-omission

API_CONTRACTS' arm bullet explicitly grants 'Disarm is the same path inverted and always succeeds for known units' -- no test calls or pins disarm in any shape (and the REST adapter currently exposes no disarm endpoint, so the contract sentence is unreflected anywhere). ADR-0003 D5 explicitly assigns EnergyServiceFacade.acknowledge_inhibit(unit_id) to this facade in the same milestone the suite was written against ('Inhibit acknowledgement (D5)' in the D2 ownership list) -- zero tests (CONTINUITY defers the actor model, so the primary must consciously record the deferral rather than let it fall silent). The facade contract paragraph also says it 'composes the intent, observation, authorization, audit, and schedule repositories, the kernel control surface...' but the pinned constructor (lines 388-398) omits schedule and kernel entirely; an implementation that never composes them passes. Extra optional kwargs are not forbidden, so nothing is blocked, but three contracted surfaces carry no behavioral pins.

Suggested fix: Either add a disarm test (requested known units always succeed, per-unit outcomes, audited/published) and an acknowledge_inhibit contract (arm scope + interactive, clears latch only, never bypasses stable-sample recovery), or have the primary record in CONTINUITY/API_CONTRACTS that disarm and inhibit acknowledgement are deferred out of this milestone and amend the facade composition sentence.

### [3] P1 - Invented peek(unit_id) authorization port is unsanctioned and discards capability expiry
Category: contract-conflict

The behavioral pin (snapshot must not consume a single-use capability, lines 575-584) is well grounded, but the only mechanism the fakes allow is a new AuthorizationRepository.peek(unit_id) method: any other non-destructive read name raises AttributeError, so the exact port name is implicitly dictated. API_CONTRACTS' port list is publish/current/revoke, and the primary's approved production-API list (which sanctioned the new actor-handle surface) does not include peek -- this is the one un-reconciled invention. Worse, the invented signature drops time: current() takes now_mono, peek() does not, and the Capability fake has no expiry field at all, while production UnitSetpoints carry a monotonic authorization expiry. Concrete scenario: an expired capability sits in the slot; the facade projects it as authorized_power == live authority; no test can fail because the fake cannot represent expiry.

Suggested fix: Reconcile the port name and signature in API_CONTRACTS before implementation (e.g. peek(unit_id, now_mono) -> Capability | None on AuthorizationRepository, or an explicit facade-facing authorization view), and give the fake Capability an expiry so a snapshot over an expired capability is pinned to authorized_power None.

### [4] P2 - Arm refusal tests cannot distinguish facade gating from exception-swallowing pass-through; refusal reasons are unbound
Category: test-gaming

FakeActorHandle.arm() itself enforces the qualified/inhibit-latched/lifecycle rules and raises a generic RuntimeError, so a facade that blindly awaits handle.arm() on every requested known unit and converts any exception into {status: refused, reason: str(exc)} passes every arm test while implementing none of the facade-side gating the contract describes ('arms exactly the requested qualified, disarmed units'; ADR D2 'allowed only when the actor reports the unit qualified and disarmed'). The reason is pinned only as a non-empty string, so unknown-unit, unqualified, latched-inhibit, and actor-failure refusals are indistinguishable to operators (the latch case matters: the operator must learn an inhibit acknowledgement is required). qualified=None (unknown state) is deformed only in health tests, never under arm.

Suggested fix: Pin distinguishable reason vocabularies or reason codes for at least the latched-inhibit case (it has a distinct operator remedy), and add an arm case with qualified=None plus a handle that would accept arming, asserting the facade still refuses -- proving the gate is not purely the actor's exception.

### [5] P2 - recent_audit's 'stable cursor' pin is near-vacuous: nothing can ever consume the cursor
Category: vacuous-assertion

The facade surface pinned by the suite (and the REST /audit endpoint) accepts only limit -- there is no cursor parameter anywhere in the system, so the cursor's value semantics are unconsumable. The assertions reduce to: key exists, equal across two identical calls under a frozen clock, and None on an empty trail. Any deterministic constant (or len(events) of the current page, or a hash) passes. Concrete scenario: implementation returns next_cursor = 'stable' always; test green; the contract's 'stable cursor' is not actually verified.

Suggested fix: Either pin concrete cursor semantics (e.g. next_cursor equals the sequence of the oldest returned event, None exactly when fewer than limit events remain) so a future paginate(limit, after_cursor) has a defined contract, or drop the field from the pinned shape until pagination exists.

### [6] P2 - Un-granted negative pins forbid legitimate implementations (rejection audit ban, 86400s latch TTL, acknowledge must not fence/zero, exactly-once active())
Category: contract-conflict

Four pins have no doc basis. (a) Lines 804-806: rejected submissions are asserted to produce no audit and no bus event -- the contract only says mutations are audited; an implementation that security-audits rejected requests fails the suite. (b) Line 890: stop intents must have duration_s >= 86400 -- an invented constant; the contract keeps latched stops alive via repository semantics ('emergency-stop intents stay active until acknowledged'), not a minimum TTL, so an implementation using a policy-derived duration fails despite honoring latch semantics. (c) Lines 969-972: acknowledgement is forbidden from fencing or requesting bounded zero -- derivable from the invalidating-event enumeration but stated nowhere; a defensively-fencing implementation (fencing only ever revokes) fails. (d) Line 562: snapshot must call intents.active() exactly once with exactly clock.monotonic() -- a call-count pin with no contract basis.

Suggested fix: Record each of these in API_CONTRACTS (or relax the assertions): allow audit of rejections, pin latch persistence by repository behavior rather than a TTL constant, state explicitly that acknowledgement neither fences nor re-zeros, and drop the exactly-once active() call-count pin in favor of the resulting projection.

### [7] P2 - Quality aggregation under-specified: stale/suspect values and age-derived staleness can report 'good'
Category: coverage-hole

The aggregation rules pinned are only all-fields-good -> 'good', any-bad -> 'bad', and no-telemetry -> 'missing'. DataQuality also defines STALE and SUSPECT, and the observation model derives age. Concrete scenarios that stay green: telemetry whose quality map is all 'stale' with an implementation returning 'good'; telemetry 500 s old (telemetry_age_s large, all fields good) reported as 'good' rather than 'stale'; a single 'suspect' field masked by an implementation that only checks for 'bad'. Operators reading snapshot.quality get fabricated optimism -- the exact failure mode the health contract forbids ('Readiness never fabricates optimism') applied to the telemetry view.

Suggested fix: Pin at least: any stale-field or age-beyond-max telemetry yields a non-good quality (specifically 'stale' if that is the intended vocabulary), and a suspect field is never reported as 'good'.
