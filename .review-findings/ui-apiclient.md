## [1] P0 - Mutation happy paths omit the Idempotency-Key the pinned adapter requires, certifying control requests the live service always refuses
Category: coverage-hole

Every mutation route in the adapter the suite claims to pin against (src/energypod/api/rest.py, mutation() lines 302-309, used by /intents, /arm, /emergency-stop, /emergency-stop/{id}/acknowledge, /units/{id}/inhibit/acknowledge) raises BoundaryError(400, "idempotency_key_required") when a valid Idempotency-Key header is absent. The client never sends one and ApiClient has no key parameter, so in production every dispatch, arm, stop, and acknowledgement -- including emergency stop -- is refused with 400 before any safety action occurs. Yet tests at lines 232-297 mock 200/202 success for exactly these header-less requests and assert their bodies as the contract. The suite thus encodes a safety-relevant misrepresentation of the boundary: a fully green acceptance contract for a console whose stop button can never work. No test asserts an Idempotency-Key header, and no refused-path test covers idempotency_key_required/idempotency_conflict.

Suggested fix: Extend the client surface additively (as was done for ApiClientError): either accept an idempotency key per mutation call or generate a canonical one per operation, and pin in each mutation test that a valid Idempotency-Key header is sent (and pinned as a stable header in the 9-endpoint bearer test). Alternatively, if the key is deliberately out of scope this milestone, coordinate with the primary and downgrade the mutation assertions to expect the 400 idempotency_key_required envelope rather than mocking success.

## [2] P1 - WS auth assertion pins a headers-in-constructor-options API that browsers do not have; blocks every viable implementation
Category: test-gaming

expect(socket.options?.headers?.Authorization).toBe(BEARER) asserts against the test's own WebSocketStub signature (url, options). The browser WebSocket constructor's second argument is `protocols` (string or string[]); passing {headers:{...}} coerces to an invalid subprotocol and throws a SyntaxError DOMException, so the client as written (client.ts lines 142-145, 208-209 cast globalThis.WebSocket to a header-capable constructor) cannot open the event stream at all in a real browser -- it throws inside openEvents(). The stub's constructor is the client's own invented interface, making the assertion near-tautological (it checks that the client uses the convention the stub was built to mirror) while failing every browser-correct alternative (subprotocol credential, first-message auth, proxy-injected header). The 'never in URL' half of the assertion is real; the options.headers half pins a fiction.

Suggested fix: Decide the actual transport mechanism with the primary (e.g., a documented subprotocol convention, a first-frame credential message, or an app-level socket wrapper that adds headers out-of-band and is itself tested), then assert on that observable channel. At minimum, keep only the real assertions (URL contains only ?after=, no token anywhere in the URL) and move the header-channel pin to the wrapper that actually owns it.

## [3] P1 - Audit cursor test pins after_sequence, a query parameter the live adapter silently ignores
Category: contract-conflict

The test asserts the path contains 'after_sequence=118' as the Load-more contract, but get_audit in src/energypod/api/rest.py (lines 332-337) binds only `limit`; FastAPI drops unknown query params, and the facade's cursor parameter (service.py recent_audit, line 349) is never reached from REST. The suite therefore certifies a pagination mechanism that re-fetches the same newest page forever, directly conflicting with UI_CONTRACTS.md Activity ('cursor pagination (Load more)'). It also contradicts the author's claim that wire details were 'verified against src/energypod/api/rest.py' -- this param cannot have been verified. Additionally, the test only checks the literal string 'after_sequence=118'; it never ties the cursor to the prior page's next_cursor, so a client that sent a hardcoded or wrong cursor would still pass.

Suggested fix: Coordinate with the primary to bind and forward the cursor in the REST adapter (pinning the param name), then keep the test. Strengthen it semantically: assert the client sends after_sequence=<previous page's next_cursor> (the AUDIT_PAGE fixture already has next_cursor: 41) rather than a bare substring.

## [4] P2 - WS error-frame test omits `details`, hiding that the client discards the stream error envelope's details field
Category: coverage-hole

The fixture at line 483 includes details: {} but the toMatchObject at 488-492 asserts only code/message/request_id. The implementation (client.ts lines 237-247) hardcodes details: null for type:'error' frames, so the stream error envelope is not surfaced verbatim -- the suite's own stated pin -- and the omission makes that undetectable. The REST envelope test (line 315) does assert details verbatim, so the two error paths are held to different standards. A real stream failure carrying diagnostic details (e.g., {unit_id, sequence}) would be silently nulled.

Suggested fix: Give the fixture a non-empty details object (e.g., {unit_id: 'MID'}) and add it to the toMatchObject; pass frame.details through in the client's error-frame branch instead of null.

## [5] P2 - WS handshake rejection (close 4401) is uncovered and inexpressible: the stub's close events carry no code
Category: coverage-hole

The adapter rejects an unauthorized events handshake with WebSocketException code=4401 (rest.py line 536) before accept, and UI_CONTRACTS.md says 'A 401 on any call' clears the token and session. The suite pins 'an unexpected close ends iteration without error' using serverCloses(), which fires listeners with a bare {} (test lines 127-132) -- the harness cannot even express a close code -- and the client's close listener ignores the event entirely (client.ts lines 254-258). Result: a console whose token expires is indistinguishable from a network drop on the stream path; the socket silently ends and the view retries forever, and the 401-clears-session contract is unenforceable here. Note the surface ignores close codes 1008 (untrusted origin / insufficient scope) too, which at minimum are worth distinguishing from a clean disconnect for the connection indicator's four separate facts.

Suggested fix: Make serverCends/serverCloses deliver {code, reason}; add a test that a 4401 close rejects the iteration with an envelope for which isUnauthorizedError(error) is true (or whatever channel is coordinated), and that a clean 1000 close ends iteration without error.

## [6] P2 - Disarm test pins an exact wire body for a route that does not exist on the pinned adapter
Category: fixture-mismatch

There is no POST /api/v1/disarm in src/energypod/api/rest.py (the author's own coordination flag #4 admits this), yet the test asserts toEqual({unit_ids: ["MID"]}) -- an exact-body pin for a speculative route. When the real route lands it will almost certainly mirror ArmRequest (a confirmation literal) and go through mutation() (Idempotency-Key required, see the P0). The strict toEqual will block adding a confirmation field to a correct implementation. The test also feeds the 9-endpoint bearer pin, so the fictional endpoint is counted as verified surface.

Suggested fix: Either drop the body assertion and keep only path/method/bearer with an explicit TODO tied to the coordination flag, or re-pin the body from the real route once it exists. Do not present the disarm body as 'pinned against the live service adapter' in the report.
