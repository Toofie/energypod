## [1] P0 - Disconnected test demands a fabricated charge value: MID never receives an observation
Category: correctness

The test slices HEALTHY_EVENTS to its first 2 frames: [snapshot(4100), observation LHS(4101)] (HEALTHY_SNAPSHOT.units order is LHS, MID, RHS). MID's observation (seq 4102), the only carrier of soc_percent=62, is never delivered, and the REST snapshot / WS snapshot frame carry no SOC field at all. The assertion `expect(mid).toHaveTextContent(/62\s*%/)` (line 549) therefore cannot be satisfied honestly: an implementation that correctly shows 'charge: no data' for a unit with no observation (exactly what the partial test demands of LHS) fails this test, while an implementation that fabricates a default SOC (e.g. hardcodes 62% for quality GOOD units without observations) passes both. That is a fabricated value presented as a measurement — the precise contract violation ('never renders fabricated or zero-filled values') this suite exists to prevent — or an outright blocker for a correct implementation.

Suggested fix: Use `HEALTHY_EVENTS.slice(0, 3)` so MID's observation arrives before the stream drops, or drop the 62% assertion and pin snapshot-sourced content only (e.g. /2,?400\s*W/ power). Do not keep an assertion whose only passing strategy is inventing a charge value.

## [2] P1 - requested/authorized/measured never diverge, so the card's power source is unpinned
Category: test-gaming

HEALTHY_SNAPSHOT MID has requested DISCHARGE 2400, authorized DISCHARGE 2400, measured_watts -2400 (lines 243-247), and the partial fixture repeats the same equality. The healthy-render assertions /discharg/i + /2,?400\s*W/ (lines 348-349) pass identically whether the card binds to requested_power, authorized_power, or measured_watts — the author's stated pin 'direction+power from measured_watts' cannot fail. Worse, /2,?400\s*W/ also matches '-2,400 W', so the sign convention of measured_watts (negative = discharge in every fixture) is unasserted. No fixture ever exercises a clamped or partially delivered action, so an implementation showing the requested 2,400 W while the safety system allowed 1,000 W sails through — the misrepresentation class ('a limited action is never presented as fully delivered') the prompt flags as safety-relevant.

Suggested fix: Add a fixture where requested={DISCHARGE,2400}, authorized={DISCHARGE,1000}, measured_watts=-950 and assert the card shows the actual figure (950 W) and does not present 2,400 W as delivered; pin the sign handling by asserting the rendered text for measured_watts=-2400 explicitly (e.g. /discharging[^\d]*2,400/i) so raw '-2,400 W' fails or is a deliberate choice.

## [3] P1 - Acknowledge success passes without any refetch: optimistic local latch-clearing is accepted
Category: test-gaming

The success test mocks getSnapshot.mockResolvedValueOnce(latched).mockResolvedValue(cleared) but only asserts postInhibitAcknowledgement was called and the acknowledge button disappears (lines 681-691). An implementation that optimistically sets inhibit=null locally on a 200 response — never refetching — passes every assertion. That contradicts the suite's own pin ('success path refetches and clears the latch') and API_CONTRACTS 'Inhibit acknowledgement': acknowledgement only clears the latch, the unit still needs stable qualifying samples to reach DISARMED and a still-present blocking fault re-latches on the next observation. Post-acknowledge state is server authority; a locally cleared view can show a unit as un-inhibited while it is still INHIBITED.

Suggested fix: After the confirm click, add `await waitFor(() => expect(client.getSnapshot).toHaveBeenCalledTimes(2));` before asserting the latch cleared, so only a refetch-driven (not optimistic) clearing passes.

## [4] P2 - Error fixtures reject with plain objects, not ApiClientError instances; module mock erases all other canonical exports
Category: fixture-shape

The snapshot-error test (line 436) and the refusal test (line 706) reject with bare `{code,message,details,request_id}` object literals. The canonical client contract (client.ts header, API_CONTRACTS) guarantees every rejection is an ApiClientError — an Error subclass carrying the envelope verbatim plus status — so an implementation that narrows rejections with `error instanceof Error` or `error instanceof ApiClientError` (a legitimate reading of that contract) renders nothing and fails, i.e. a correct-shaped implementation is blocked. Compounding it, the module factory `vi.mock("../../api/client", () => ({ createApiClient: vi.fn() }))` (line 25) makes every other canonical export undefined at runtime, so the view cannot even reference ApiClientError/isUnauthorizedError without crashing under this suite. The shared-stub agreement (mock only createApiClient) is preserved by spreading importOriginal rather than replacing the whole module.

Suggested fix: Keep createApiClient as the only replaced export but preserve the rest: `vi.mock("../../api/client", async (importOriginal) => ({ ...(await importOriginal<typeof import("../../api/client")>()), createApiClient: vi.fn() }))`, and reject with `new ApiClientError({ ...envelope, status: 503 })` so the view sees the documented rejection shape.

## [5] P2 - Zero-filled fabricated values are not excluded: negatives only forbid the '%' and 'mV' tokens
Category: coverage-hole

The never-fabricate guards are `expect(lhs).not.toHaveTextContent(/%/)` (line 525) and `expect(rhs).not.toHaveTextContent(/mV/)` (line 532). 'Charge: 0' or 'Spread: 0' contain neither token and pass, violating 'never renders fabricated or zero-filled values presented as measurements'. The hole is live for power too: partial-fixture LHS has measured_watts null, yet nothing forbids rendering '0 W'/'Idle' as if it were a measurement on the disconnected card — only the % token is excluded. The positive assertions (label present + 'no data' somewhere on the card) do not tie the 'no data' text to each specific missing field.

Suggested fix: Scope to the row: locate the charge/temperature/cell rows within the card (e.g. within(lhs).getText or a row query by /charge/i) and assert each row's own text matches /no data/ and contains no digits; add a missing-power case forbidding /0\s*W/ on a unit whose measured_watts is null.

## [6] P2 - No reconnect assertion after stream drop or retry: cursor-carrying resubscribe is unpinned
Category: coverage-hole

UI_CONTRACTS 'Data sources' pins that on connection loss the console retries 'with the last sequence as the cursor when reconnecting'. The disconnected test (lines 540-554) stops at asserting the /disconnected/ notice and retained cards, and the error-recovery test (line 448) stops at the cards reappearing — neither asserts openEvents was called again nor with which cursor. The mock already returns a replayable iterable, so an implementation that shows the notice and then never resubscribes (frozen data behind a notice, indefinitely) passes. Note the last delivered sequence here is 4101 (LHS observation), which also makes a nice cross-check that the cursor is the last seen sequence rather than the snapshot's 4100.

Suggested fix: After the disconnected notice, assert `await waitFor(() => expect(client.openEvents).toHaveBeenCalledTimes(2))` and `expect(client.openEvents).toHaveBeenLastCalledWith(<last delivered sequence>)`; optionally the same for the post-retry path.

## [7] P2 - Summary and Details tab contents have zero assertions; Details is never activated
Category: coverage-hole

The keyboard test asserts the four tab roles exist (lines 566-569) but only ever activates Summary (initial) and Cells; the Details tab is never opened in any test, and the Events test is the only other panel whose content is checked. UI_CONTRACTS pins concrete content per tab: Summary = 'condition, power, limits, communications, recent trend'; Cells = '... data completeness'; Details = 'advanced measurements and data-quality map'. None of that is asserted — an implementation rendering empty panels behind the Summary and Details tabs passes. The Cells panel check covers min/max/spread/temperatures but not data completeness (cell_data_age_s is available in the fixture and unused there).

Suggested fix: Extend the keyboard flow: ArrowRight twice to Details and assert at least a data-quality element (e.g. /quality|data/i text); assert the Summary panel shows condition/power/limits or communications wording; add a completeness assertion to the Cells panel (e.g. cell data age or /completeness/i).

## [8] P2 - Focus-trap check cannot distinguish a trapping dialog in the common case
Category: accessibility

The trap check is one Tab press (lines 742-743) after the dialog opens. Unless focus happens to start on the dialog's last focusable element, a single Tab lands on the next focusable inside the dialog with no trap installed — a non-trapping dialog passes. The contract pin ('dialogs trap and restore focus') and the author's own report claim a focus trap; what is proven is only 'focus is inside the dialog at open and after one Tab'. Escape-cancel, focus restore, and API-not-called checks in the same test are real and do fail appropriately.

Suggested fix: Tab through every focusable in the dialog until focus would leave (or Tab from the last focusable, e.g. via end-of-dialog detection or a bounded tabUntil loop) and assert focus wraps to the first focusable inside the dialog; a Shift+Tab from the first focusable wrapping to the last is the complementary check. (Relatedly, the contract's assertive live-region announcement for a newly latched inhibit is unasserted anywhere in the suite — worth pinning or explicitly deferring to the shell suite.)
