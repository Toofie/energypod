## [1] P0 - Requested/allowed/actual magnitudes never bound to their labels: swapped figures (allowed shown as requested) pass
Category: test-gaming / safety misrepresentation unpinned

The test asserts /requested/, /allowed/, /actual/ (lines 280-282) and then /3,?000/, /1,?200/, /1,?150/ (lines 284-286) as six independent expectVisibleText calls inside the unit entry. Nothing binds a magnitude to its label, so an implementation rendering "Requested 1200 W / Allowed 3000 W / Actual 1150 W" — the exact 'allowed shown as requested' misrepresentation UI_CONTRACTS.md forbids ("a limited action is never presented as fully delivered") — passes all six assertions plus the loose note regex /limit|reduc|less than requested|holding back/ (any occurrence of the word "limit" satisfies it). The 'Limited' badge it.each case only proves the implementation compared the numbers internally; the presentation is unpinned, and no other test in the suite pins the pairing. Contrast the parallel NowView suite, which does it correctly: findByRole("group", { name: "Requested" }) then textContent toMatch(/1,?200\\s*W/).

Suggested fix: Assert per labeled node: within(entry).getByRole("figure" or "group", { name: /requested/i }) and expect its textContent to match /3,?000/ (likewise allowed->1,200, actual->1,150), or use one combined regex per figure (e.g. /requested[^]*3,?000/). Also tighten the limit-note assertion to bind the authorized magnitude (e.g. /limit(?:ed)?[^]*1,?200/).

## [2] P1 - Fixture wire values contradict the real serialization: uppercase enums and an impossible quality 'STALE'
Category: fixture envelope-shape violation

The suite header (lines 17-23) claims the literals 'are exactly what the view receives' per the documented shapes, but the real serializer emits lowercase values: service.py _enum_value (line 145) returns StrEnum values ('disarmed', 'armed_idle', 'active', 'inhibited', 'observe_only' per domain/observations.py lines 23-28; 'charge'/'discharge'/'idle' per domain/intents.py lines 11-13), and tests/api/conftest.py lines 73-77 pin the lowercase wire. Worse, quality 'STALE' (line 508) and 'SUSPECT' (line 42) cannot occur at all: _quality_projection (service.py lines 869-883) only ever emits 'good'/'degraded'/'bad'/'missing', so real stale data arrives as quality 'degraded' with telemetry_age_s past the 30s freshness bound (service.py line 44). The author flagged enum casing to primary, but not the impossible quality values, and the in-suite comment still asserts fidelity. An implementation keyed to these fixtures has dead lifecycle/quality branches against the live API while the suite stays green; one keyed to the real lowercase wire fails the badge, stale, and limiting tests.

Suggested fix: Rewrite fixtures with the real lowercase wire values, derive the stale case from telemetry_age_s > freshness bound with quality 'degraded' (never quality 'STALE'), and either drop the fidelity claim in the header comment or reconcile client.ts types at the same time.

## [3] P1 - Expiry-countdown assertion demands data no pinned source carries and is satisfied by any incidental 'expiry'/'remaining' word
Category: assertion cannot fail meaningfully / unimplementable pin

The test requires text matching /expire|ends? in|remaining|countdown/ (line 315), but no data source the suite pins carries an expiry: the facade snapshot unit view (service.py _unit_view) has only lifecycle/telemetry_age_s/quality/requested_power/authorized_power/measured_watts, the fixture stream contains only the snapshot frame (no intent.accepted event with ttl/expires_at), and getAudit is fixed to {events: []}. An honest implementation has nothing to compute a countdown from, while the regex is satisfied by any incidental mention ('expiry', 'remaining time unknown'), so the contract's 'expiry countdown' is simultaneously unimplementable-from-fixture-data and effectively unpinned — yet it is reported as covered. The direction/watts parts (lines 313-314) are fine.

Suggested fix: Extend the stream fixture with an intent frame carrying expiry (e.g. {type: 'intent.accepted', direction, watts, expires_at or ttl_s}) and assert a concrete countdown ('ends in' plus a number/unit derived from that field), or drop the countdown pin and record that the pinned snapshot wire cannot supply it.

## [4] P1 - Loading/error/refused tests assert 'no unit data' while the default live socket streams the authoritative snapshot
Category: fixture incoherence / blocks a contract-legitimate design

installClient's openEvents default (line 156) is liveStream(snapshot), which yields the authoritative snapshot frame immediately. The loading test (lines 435-447) asserts queryByText(/pod-mid/) is null; the error test (line 564) and refused test (line 589) assert the same after awaiting findAllByText — by which point the microtask-delivered WS snapshot has arrived. The contract makes that frame authoritative ('authoritative snapshot envelope first'), so a correct stream-first implementation renders pod-mid and deterministically fails the error/refused tests (the loading test passes only because its assertions run synchronously before the microtask flush — brittle). The fixtures thereby encode an unproven pin ('never render stream data when a REST read fails or pends') in an impossible world (REST refuses with insufficient_scope while the same-credential socket happily streams units).

Suggested fix: In the loading, error, and refused setups, pass an explicit openEvents that is either never-resolving or failing (e.g. an async generator that awaits forever or rejects), so 'no unit data' is asserted against a world where no data exists.

## [5] P1 - resync_required discontinuity path never driven for Home even though HomeView owns its socket
Category: contract requirement omitted for this view

UI_CONTRACTS.md 'Data sources' pins: 'resync_required (any reason) triggers a snapshot refetch and reconnect'. HomeView demonstrably owns its socket lifecycle (the disconnected test reconnects via openEvents(42)), yet no Home test ever sends a resync_required frame — an implementation that ignores resync markers on Home passes 17/17. The parallel NowView suite covers resync only for its own view (NowView.test.tsx line 213), so unless HomeView shares that hook the behavior is unpinned where it matters; the suite as acceptance contract leaves the discontinuity path untested for Home.

Suggested fix: Add a case whose stream yields the snapshot frame then {type: 'resync_required', reason, snapshot_sequence}, asserting getSnapshot is called again and openEvents is reconnected with the last seen sequence (42) as cursor — mirroring the NowView pattern.

## [6] P2 - Error rejections are bare envelope objects, not the ApiClientError the pinned client contract yields
Category: fixture infidelity vs pinned client contract

The error and refused tests reject with plain envelope objects (lines 552-558, 581-582), but the client module this suite imports and mocks documents that 'every failure crossing this boundary rejects with this [ApiClientError]' (client.ts lines 19-25, 93-107) carrying code/message plus status. A view that narrows rejections with instanceof ApiClientError — following the documented contract of its only compile-time dependency — fails these tests and is forced onto duck-typing, while the suite comment (line 61) presents the bare object as 'the API error envelope ... verbatim'. The rendered-text pins themselves (exact 'internal_error'/'The request could not be completed', 'insufficient_scope'/'The credential lacks permission') are good.

Suggested fix: Reject with a real ApiClientError instance (or at minimum an Error carrying code/message/status fields) so the rejection shape matches what the pinned client actually yields at this boundary.

## [7] P2 - Vestigial length assertions that cannot fail, and expectVisibleText checks visibility of only the first match
Category: assertions that cannot fail

expect(await screen.findAllByText(...)).not.toHaveLength(0) at lines 486, 562, and 586 can never fail — findAllByText already throws on zero matches, so the expect is dead weight; the same pattern applies to getAllByText plus toBeGreaterThan(0) inside expectVisibleText (line 196) and dataLanded (line 215). Relatedly, expectVisibleText checks visibility of only matches.at(0), so a hidden first match plus a visible later duplicate passes, weakening the 'visible' guarantee the helper name promises. Harmless to outcomes today, but it masks which assertions are actually load-bearing.

Suggested fix: Delete the vestigial .not.toHaveLength(0) and length>0 expects (keep the awaited findAllByText), and have expectVisibleText assert that at least one match (not just .at(0)) is visible.

## [8] P2 - Disconnected notice detectable via leaked raw error text; no live-region or focus-order accessibility assertions
Category: accessibility coverage hole / gameable assertion

Two gaps. (1) findAllByText(/disconnect|connection lost|reconnect/i) at line 485 passes if the view merely prints the thrown Error's own message ('connection lost' — see failingStream line 132) rather than rendering a designed per-view notice, so the disconnected-notice pin is gameable by error-text leakage. (2) The test conventions require explicit accessibility assertions across 'roles, names, live-region announcements, focus order'; this suite covers roles/names and one tab-reach flow but has zero live-region assertion (the shell contract's polite status-change announcements and assertive emergency announcements land on content Home renders, e.g. lifecycle changes arriving over the socket) and no focus-order check beyond reaching a single button. Nothing fails if the five regions never announce updates.

Suggested fix: (1) Make failingStream throw an opaque error ('socket boom') and require a designed notice (e.g. role='status' or text /disconnected|reconnecting/ that cannot come from the error message). (2) Add a case where a second stream frame changes a unit lifecycle and assert the change is announced via an aria-live region (getByRole('status' or 'alert') textContent updates).
