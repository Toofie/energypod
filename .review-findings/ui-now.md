## [1] P1 - intent.accepted WS fixture flattens the payload; real frames nest fields under "payload"
Category: envelope-fixture

The fixture frame is {type:'intent.accepted', sequence, occurred_at, principal, intent_id, direction, watts, unit_ids} all at top level. The implemented backend publishes {type, payload:{principal,intent_id,direction,watts,unit_ids}} (service.py:1008-1009 `self._events.publish({"type": event_type, "payload": dict(payload)})`), the bus adds only sequence/occurred_at (events.py:43-54), and rest.py sends the envelope unchanged (rest.py:716). The client stub yields frames untransformed (client.ts streamEvents/parseFrame). So a view correctly reading frame.payload.direction fails this test's discharge/1,200 W waitFor, and a view written to pass the test (top-level fields) sees nothing when run against the real stream. Adjacent nit: resync reason 'discontinuity' (line 219) is not a real reason string (rest.py/events.py produce non_monotonic_event, sequence_gap, backpressure, slow_subscriber, retention_window_exceeded, invalid_snapshot).

Suggested fix: Change the frame to {type:'intent.accepted', sequence:42, occurred_at:'...', payload:{principal:'operator', intent_id:'intent-2-1.000000', direction:'discharge', watts:1200, unit_ids:['MID']}} and use a real reason string such as 'sequence_gap'.

## [2] P1 - Emergency-stop fixture uses degraded:false; the real envelope's degraded is a list of reason strings
Category: envelope-fixture

service.py:689-695 returns {"stop_id": stop_id, "status": "latched", "unit_ids": sorted(selected), "fenced_generation": fenced_generation, "degraded": degraded} where degraded is a list built via append (e.g. ['bounded_zero_failed:MID'], 'audit_unavailable'). The fixture's degraded:false invites boolean handling ('degraded ? ...') that mislabels or crashes on the real list; a degraded stop is exactly the case the operator must see rendered faithfully. The author's report claims fixtures were copied from the implemented API, so this is drift, not intent.

Suggested fix: Use degraded: [] in the happy path and consider a second fixture (or a follow-up test) with degraded:['audit_unavailable'] asserting the degradation is surfaced.

## [3] P1 - Allowed fact is never pinned for authorized_power:null with a live request — the limited/refused-to-zero misrepresentation passes the suite
Category: coverage-hole

The requested/allowed/actual distinction is only tested with all three values present (ACTIVE_MID: 1500/1000/980). In the only null-authorized fixture (test at line 287 and ARMED_MID), requested_power is idle/0 and only the Actual fact is asserted; no test has requested_power non-idle with authorized_power null, which is a real state (service.py _unit_view: requested_power comes from active intents, authorized_power from an independent capability peek — an accepted-but-not-yet-granted or revoked intent). An implementation that echoes the requested watts into the Allowed fact when authorized is null would pass every test in the file, which is precisely the 'a limited action is never presented as fully delivered' failure the contract forbids. Also no multi-unit partial case (some units reporting, one missing) exists for this card.

Suggested fix: Add a snapshot with requested_power {charge,1500}, authorized_power null, measured_watts null and assert the Allowed fact renders an explicit none/not-yet-authorized value and does NOT match /1,?500/.

## [4] P1 - WS-first-frame snapshot adoption is claimed but never proven — only intent-event adoption is pinned
Category: assertion-strength

In the WS adoption test, the waitFor goes straight to the post-event state (discharge 1,200 W), so a view that ignores snapshot frames and applies only intent.accepted events passes. In the resync and disconnected tests, getSnapshot resolves the identical envelope, so REST can be the sole data source; the resync test asserts only call counts. Nothing in the suite discriminates WS-snapshot adoption from REST adoption, yet 'the first WS frame is the authoritative view' is the behavior the test name and the report claim to pin.

Suggested fix: Split the stream: assert requested shows charge/1,500 W from the {type:'snapshot'} frame first (REST still pending), then deliver intent.accepted and assert the update; or in the disconnected test make REST never resolve a second time so the visible facts can only come from the frame.
