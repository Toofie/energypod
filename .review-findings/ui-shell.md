## Review summary

Findings below are ranked most severe first.


## [1] P0 - Lifecycle fixtures use UPPERCASE values the service can never send, blocking a correct implementation
Category: fixture/envelope-shape violation

The suite's UnitView union (lines 55-60) pins lifecycle values OBSERVE_ONLY/DISARMED/ARMED_IDLE/ACTIVE/INHIBITED, and the header (lines 42-44) claims they 'follow the fleet coordinator's vocabulary'. They do not: the service serializes lifecycle via _enum_value (src/energypod/application/service.py:145-147,863) of the StrEnum in src/energypod/domain/observations.py:22-30, whose wire values are lowercase 'observe_only'/'disarmed'/'armed_idle'/'active'/'inhibited', plus three more states the suite's type forbids (boot, stopping, disconnected). Because client.ts passes snapshots through verbatim, an implementation that consumes the real envelope matches nothing and fails every banner/announcement test; only an implementation special-cased to the suite's uppercase fixtures can go green, and against the live API it would render no/wrong banner state. The author's reconciliation pin (3) flags NowView's lowercase as the outlier, but NowView is the suite that matches the actual service.

Suggested fix: Change fixtures to the real lowercase StrEnum values (and note the casing decision in client.ts or a shared normalizer test instead of per-suite pins), widen the lifecycle type to include boot/stopping/disconnected, and add a case for how the banner behaves for the extra states (e.g. disconnected units conservatively).

## [2] P1 - Invented WS event types with flat payloads diverge from the service's actual event vocabulary
Category: fixture/envelope-shape violation

The suite pushes {type:'unit.lifecycle', unit_id, lifecycle}, {type:'unit.inhibit_latched', unit_id, reason_code}, {type:'unit.stop_latched', unit_id, stop_id} with unit fields at the top level (lines 650-656, 674-680, 695-701). No such types exist server-side: the backend emits unit.armed, unit.disarmed, intent.accepted, observation.published/updated, decision.updated, authorization.revoked, audit.appended (src/energypod/application/service.py:501,533; runtime/composition.py:393,451,533; tests/api/test_event_contract.py:126-127), and real bodies carry the unit facts under a 'payload'/'data' wrapper, not flat. API_CONTRACTS.md contemplates 'lifecycle... and stop events' but never names them. A green AppShell built to these tests reads frame.unit_id and dispatches on names the real stream never sends, so the polite/assertive announcement requirements are pinned against vocabulary that cannot occur; the suite header's claim that fixtures 'mirror the REST/WS shapes in docs/API_CONTRACTS.md' is false for these frames.

Suggested fix: Either use the emitted names (unit.armed/unit.disarmed for lifecycle transitions; the stop/inhibit events actually published or their documented names once pinned) with payload/data-wrapped unit fields, or explicitly flag in the reconciliation notes that these types are new API surface that the service must grow, and structure fixtures as {type, sequence, payload:{...}} to match the event-bus body convention.

## [3] P1 - Polite-announcement assertions match the OLD state: /armed/i passes on stale 'Disarmed' text
Category: assertion cannot fail

Lines 663 and 840 assert the polite live region matches /armed/i after a DISARMED->ARMED_IDLE transition. 'Disarmed' contains the substring 'armed', so an implementation that seeds the announcements region once with the initial status ('Disarmed') and never announces the change passes both the normal and the reduced-motion test. The assertion cannot fail for exactly the bug it exists to catch (no announcement on change). Note the banner assertion right before it (expectVisibleText(banner(), 'Armed') with exact string matching) is precise; only the live-region check is broken.

Suggested fix: Use /\bArmed\b/ (word boundary excludes 'Disarmed'), or assert the announcement text names the unit and the new state, e.g. toMatch(/MID/) and toMatch(/\barmed\b/i), and optionally assert the region did not merely retain pre-existing text.

## [4] P1 - resync happy path and reconnect-with-last-sequence cursor are untested; the stream mock contradicts the pinned client's resync semantics
Category: coverage hole / mocked-away contract

UI_CONTRACTS 'Data sources' requires: resync_required (any reason) triggers a snapshot refetch AND reconnect, and connection loss retries 'with the last sequence as the cursor when reconnecting'. The suite only drives resync -> refetch 401 -> entry (lines 427-439). Never tested: refetch succeeds and data continues at the new sequence; openEvents is re-invoked with the last seen sequence as the after cursor (the afterSequence parameter appears only in the interface at line 190 and is ignored by every mock, lines 206-214, so cursor behavior is structurally unassertable here). Compounding this, the suite's streamChannel (lines 135-173) keeps the generator alive after yielding resync_required, whereas the pinned client ends iteration immediately after resync_required (client.ts:231-235) and on unexpected close (client.ts:254-257) — the suite never simulates stream termination, so the shell's reconnect-on-generator-return path, the very mechanism the real client uses, is never exercised. This also deviates from the UI_CONTRACTS test convention of mocking at the fetch/WebSocket boundary.

Suggested fix: Add a happy-path resync test: channel yields resync_required then ENDS (mirroring client semantics), assert getSnapshot refetches and openEvents is called again with the last seen sequence as its argument; add the same cursor assertion to the stream-lost test; make the default openEvents mock record its afterSequence argument.

## [5] P1 - Global-shell Stop-reachability and dialog focus-trap bullets omitted entirely
Category: coverage hole (safety-relevant)

The suite's header claims to pin UI_CONTRACTS 'Global shell behavior', which includes 'Stop is reachable from every screen that can initiate or display active control (one action, then a confirmation dialog with the affected units)' and 'dialogs trap and restore focus'. Neither is tested anywhere: grep finds no emergency-stop/d/dialog/focus-trap assertions; postEmergencyStop mocks exist only as unused stubs (lines 203, 371). Home displays active control ('what is powering the home now', current power figures), so shell-level Stop reachability from Home, the confirmation naming the affected units, and focus trap/restore are all unpinned — and no other suite is positioned to pin the cross-view reachability guarantee. The nav tests stop at aria-current switching.

Suggested fix: Add: with a unit ACTIVE on Home, a Stop control is reachable by keyboard, activating it opens a dialog that names the affected units and traps focus, Escape/confirm restores focus, and the shell renders it from every view that displays active control (at minimum Home and Now).

## [6] P1 - Disconnected operator state and last-data retention unpinned; data may vanish silently on stream loss
Category: coverage hole (state contract)

The stream-lost tests (lines 595-618, 708-739) assert only that the 'event stream' fact flips to FACT_NO (plus an assertive alert when control is active). The contracted disconnected presentation — 'banner + per-view notice, last data dimmed with age' — is never asserted: an implementation that silently removes all fleet data and shows no operator-visible disconnected notice (when not in active control) passes. There is also no assertion that the last snapshot remains rendered with its age, which is the operator's only honest view of 'how old is what I am looking at' during an outage.

Suggested fix: After channel.fail, assert (a) a visible disconnected notice (distinct from the four-fact indicator), (b) the last-known unit data (MID etc.) is still rendered, dimmed/not hidden, with its data age shown, and (c) in the non-active-control case (no alert expected) the operator still learns the stream is down.

## [7] P2 - Wrong-token envelope assertions are weaker than 'verbatim': tautological length check, code and message may land in unrelated nodes, no accessible role
Category: weak/tautological assertion

Line 354: expect(await screen.findAllByText('invalid_token')).not.toHaveLength(0) — findAllByText already rejects when it finds nothing, so the length check adds nothing (tautological), and both this and expectVisibleText(document.body, 'That access token is not valid.') (line 355) allow the code and the message to appear in unrelated nodes anywhere in the page, not together as the rendered rejection envelope the contract requires ('MUST surface rejection envelopes verbatim (code + message)'). Additionally, no accessible role is required for the refusal: a visually-styled but unannounced div passes, leaving screen-reader operators with no announced reason the unlock failed — notable given the suite otherwise pins live-region semantics carefully.

Suggested fix: Scope both strings to a single element: const notice = await screen.findByRole('alert') (or role=status on the entry form); assert within(notice).getByText('invalid_token') and within(notice).getByText('That access token is not valid.') — and drop the redundant length assertion.

## [8] P2 - Reduced-motion test cannot distinguish honored vs ignored; health fixture type conflict with the shared client stub is unlisted
Category: accessibility assertion checks nothing / type conflict

The reduced-motion test (lines 810-841) stubs matchMedia but never asserts it was consulted: an implementation that ignores prefers-reduced-motion entirely (always animates in real browsers) passes, because jsdom renders no animations and the test only re-runs the same flow with a different stub value. The suite's real pin is only 'does not crash when the query matches'. Separately, the health fixtures (nested {liveness:{ok},service_readiness:{ready,reasons},control_readiness:{ready,reasons}}) correctly match rest.py's actual envelope but contradict the shared client.ts stub's Health interface (flat strings, client.ts:58-62) and are smuggled through 'as unknown as ApiClient' (lines 216, 376), so tsc cannot surface the drift — and this conflict is missing from the reconciliation pins (the pins list the lifecycle-casing conflict only). A green implementer typing against client.ts will read .ready off a string.

Suggested fix: Capture the matchMedia stub as a vi.fn and assert it was queried with '(prefers-reduced-motion: reduce)' (or assert the implementation reads the media query); add a reconciliation pin recording that the client.ts Health interface must be corrected to the nested service shape, and remove the 'as unknown' double cast once the types agree.
